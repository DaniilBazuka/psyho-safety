# 🔍Как работает git pull (что под капотом)? Но в целом могут спросить как работает любая из команд, перечисленных в блоке теории.


`git pull` часто воспринимают как одну команду, но **под капотом это макрос**, который выполняет две последовательные операции:

	bash
		git fetch <remote> <branch>
		git merge FETCH_HEAD   # или git rebase, если настроено

### 🔍 Этап 1: `git fetch` (сетевое взаимодействие)

1. **Контакт с удалённым репозиторием**  
    Git обращается к `origin` (или другому указанному remote) по протоколу HTTP(S) или SSH.
2. **Обмен "хотелками"**  
    Локальный Git отправляет список хешей коммитов, которые у него уже есть. Удалённый сервер отвечает: _"Вот новые объекты, которых у вас нет"_.
3. **Скачивание объектов**  
    Git загружает пакеты (`packfiles`) с коммитами, деревьями и блобами. Всё сохраняется в `.git/objects`. **Рабочая папка и индекс пока не меняются.**
4. **Обновление remote-tracking refs**  
    Локальные указатели на удалённые ветки двигаются:  
    `origin/main` → обновляется на актуальный хеш с сервера.  
    Ваша локальная ветка `main` и `HEAD` **остаются на месте**.

✅ После `fetch` вы видите свежие данные, но ничего не сломано. Можно изучить изменения через `git log origin/main` или `git diff main..origin/main`.

### 🔍 Этап 2: Интеграция (`merge` или `rebase`)

Сразу после `fetch` Git пытается влить изменения в вашу текущую ветку. Поведение зависит от настроек.

#### 🟦 Вариант A: По умолчанию (`git merge`)

	bash
		git merge origin/<branch>

1. Git находит **общего предка** (common ancestor) между вашей веткой и `origin/...`.
2. Сравнивает три версии:
    - `BASE` (общий предок)
    - `OURS` (ваша ветка)
    - `THEIRS` (удалённая ветка)
3. **Два сценария:**
    - **Fast-Forward**: если ваша ветка не ушла вперёд, Git просто сдвигает указатель ветки на новый коммит. Рабочие файлы обновляются.
    - 🔵 **Merge Commit**: если были локальные коммиты, Git создаёт новый коммит слияния (`Merge branch '...' into ...`), объединяя деревья. Рабочая папка и индекс обновляются.
4. При пересечении правок в одних строках → **конфликт слияния**. `pull` останавливается, просит разрешить вручную.

#### 🟨 Вариант B: Режим rebase (`pull.rebase=true` или `--rebase`)

	bash
		git rebase origin/<branch>

1. Git временно "откладывает" ваши локальные коммиты в сторону.
2. Перемещает указатель ветки на `origin/...`.
3. По одному применяет ваши коммиты поверх.
4. Если конфликты → процесс паузится, вы разрешаете, затем `git rebase --continue`.
5. **Итог:** история линейная, merge-коммитов нет, но хеши ваших коммитов изменятся.

### Что происходит с файлами и индексом?

- Пока идёт `fetch` → файлы на диске **не трогаются**.
- На этапе `merge/rebase` Git:
    1. Обновляет **индекс** (staging area) под новое состояние.
    2. Перезаписывает **рабочую директорию**.
    3. Если в рабочей папке есть **незакоммиченные изменения**, которые конфликтуют с incoming-изменениями → `pull` **отказывается запускаться** с ошибкой `Your local changes to the following files would be overwritten by merge`.

### ⚙️ Полезные флаги и настройки

| Команда \Настройка                       | Что делает                                                                                                   |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| git pull --ff-only                       | Разрешает только fast-forward. Если нужен merge-commit → отменяет операцию. Безопасно для CI/CD.             |
| git pull --rebase                        | Принудительно использует rebase вместо merge.                                                                |
| git config --global <br>pull.rebase true | Делает rebase поведением по умолчанию для всех репозиториев.                                                 |
| git pull --no-commit                     | Выполняет merge, но не создаёт коммит и не обновляет HEAD. Позволяет проверить состояние перед финализацией. |
### 💡 Почему опытные разработчики иногда избегают `git pull`?

`pull` удобен, но **скрывает промежуточное состояние**. Многие предпочитают:

	bash
		git fetch
		git log --oneline HEAD..origin/main   # посмотреть, что прилетело
		git merge origin/main                 # или rebase, осознанно
Это даёт контроль: можно отменить слияние, если изменения неожиданные, или разрешить конфликты в чистом контексте.

### 🧠 Короткая схема под капотом

	git pull
		   1. Сеть: скачиваются объекты → .git/objects
		   2. Ссылки: обновляется origin/ветка
		   3. Проверка: нет ли dirty working tree?
		   4. Интеграция:
		        сли pull.rebase=false → git merge origin/ветка
		        если pull.rebase=true  → git rebase origin/ветка
		        обновление index + working tree + HEAD
